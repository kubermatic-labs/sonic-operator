# Declared site artifacts and agent recovery

## Overview

`SwitchArtifact` is a namespaced resource that declares and enforces one switch's artifact bundle: the agent binary, its systemd unit and TLS material, and optional platform files such as Python platform packages. Use it when you want the operator to install, update and roll back these files on a switch instead of managing them by hand.

Key properties:

- Every file has a typed destination slot, a SHA256 and an ordered list of references to immutable ConfigMap chunks in the resource's namespace.
- Certificate, private key and CA slots require references to immutable Secrets.
- Every reference includes the source object's UID, so deleting and recreating an object cannot substitute different content.
- The controller resolves and checks the actual content before staging, and rechecks the declaration, target and source identities immediately before mutation.
- The CRD and runtime validators reject arbitrary paths, unit text and shell commands. Agent service arguments are generated from typed options.
- An independent supervisor on the switch performs installation and rollback. It requires an independently installed, root-owned baseline policy whose exact SONiC image hash and platform destination map match the host.

## How it works

### Independent supervisor

The main agent exposes `ArtifactService` on its existing mandatory mTLS listener. It talks to an external supervisor over a root-only Unix socket. The agent process does not own the rollback timer or the installation; the supervisor does.

- The generated main-agent unit has an ordering dependency on the supervisor (but no hard `Requires=`), so the agent can still start and repair bootstrap drift if the supervisor cannot start.
- The supervisor uses `Type=notify`. Confirmed boot inputs are restored before rc-local, platform-module installation and native platform services are released.

### Activation modes

**AgentRestart**

1. Content is staged and verified, and recovery metadata is durably recorded.
2. The supervisor atomically installs the files and restarts the agent.
3. The controller reconnects over mTLS and obtains fresh health evidence before confirming the transaction's random token, which is bound to owner, target and generation.

A bundle can keep its platform files unchanged while rotating the agent or its certificates. That operation does not reinstall packages or restart ASIC services.

**PlatformNextBoot**

- Changed inputs wait for a new cold-boot identity before installation. Fast/warm reboot with ASIC reuse is not qualified for changed platform inputs.
- The operator never initiates a reboot remotely.
- A five-minute confirmation window starts on activation.
- Inputs that are already installed and proven are not rewritten or restarted. A first platform import still needs guarded provenance activation, and missing loaded-TLS evidence still requires a restart.
- Platform activation runs only after native startup and installation jobs have settled. The qualified wheel's exact package tree and metadata are installed under a transaction fence, and the existing pmon container is kept. Independent timeouts bound orphaned installers.
- Qualified Python daemons restart under an isolated import-provenance wrapper. Changed ASIC inputs also regenerate swss/syncd.

### Rollback behavior

- An interrupted partial installation rolls back.
- An unconfirmed agent update or certificate renewal rolls back after five minutes, even if the agent or controller dies. The deadline uses boot identity and monotonic uptime, so an NTP wall-clock step cannot extend it.
- Recovery has its own process identity and health verification. If health fails, the phase stays `RollingBack`; recovery is never reported as successful merely because files were copied.
- Last-confirmed content stays available for boot restoration after a failed update. Drift observed before a new attempt does not replace the last-confirmed rollback version.
- Pre-install compare-and-swap conflicts preserve local edits.

### Bootstrap ownership

The first reachable main agent that supports `ArtifactService` is the deployment's trust seed. After that, **`SwitchArtifact.spec.bootstrap` owns three fixed files**: the supervisor binary, its canonical unit and the baseline policy.

- Supervisor and policy bytes come from immutable, UID-pinned ConfigMaps. The unit is generated by the protocol and has a declared SHA256.
- The agent's separate `Bootstrap` RPC enforces these three fixed paths and their running/boot state before the controller attempts any artifact writes.
- The durable owner/hash record is `/host/sonic-operator-artifact-bootstrap/owner.json`. It contains no binary or policy bytes.
- An interrupted bootstrap installation resumes from the same cluster inputs.
- Changing the bootstrap identity requires an explicit baseline migration. Normal agent updates preserve the independent recovery baseline. See [Migrating the bootstrap baseline](#migrating-the-bootstrap-baseline).

### Migrating the bootstrap baseline

`spec.bootstrap` is immutable, with one exception: to accept a new agent build you can replace the supervisor and policy on the **existing** SwitchArtifact. Never delete and recreate the resource; the switch records its UID as the owner of the bootstrap, the artifact journal and the host recovery suite.

1. Build the new agent and supervisor and compose a policy whose `agentBuilds` contains both the currently running build (for rollback) and the new one. Keep `baseline`, the image hash and platform fields unchanged.
2. Publish the new supervisor chunks and policy as immutable ConfigMaps.
3. On the switch, move `/host/sonic-operator-artifact-bootstrap/owner.json` aside. The running agent rejects a different bootstrap identity while that record exists.
4. Update the SwitchArtifact: set the new `supervisorSHA256`, `supervisorChunks`, `policySHA256` and `policyRef`, and set `spec.bootstrapMigrationFrom` to the **previous** `policySHA256`. The API rejects the change otherwise, and also if `hostRecovery` or `unitSHA256` differ.
5. Wait until the agent has installed and activated the new bootstrap and the resource is Verified again. Then update the `AgentBinary` slot to the new build through the normal guarded update; the supervisor rolls back automatically if the controller doesn't confirm it within five minutes.

The running agent must understand the new policy. An agent that does not support every capability declared in the new policy cannot install it and has to be replaced out of band first.

### Journal and content store

The metadata journal records identities, hashes, modes, deadlines and state. It does not contain artifact bytes or Secret values. Separate private content files hold the staged and previous material needed for recovery.

- Content-store directories are `0700` and files `0600`. Do not publish the private recovery content store.
- Destination paths reject symlinks and untrusted ownership or writability, use confined filesystem resolution, and fsync atomic replacements and directory creation.

## Prerequisites and permissions

### Enable gates

Management requires all three of:

| Component | Setting |
|---|---|
| Operator | `--allow-artifacts=true` and `--observe-only=false` |
| `SwitchArtifact` | `managementPolicy: Manage` |
| Agent | `--allow-artifacts=true` and `--read-only=false` |

### Seed unit

The seed agent unit needs the artifact write gate and filesystem access to the fixed bootstrap destinations. A unit with `ProtectSystem=strict` that only allows writes to `/etc/sonic` and `/host` cannot bootstrap executables, units or TLS policy. Update the initial unit when you enable this capability; a managed unit cannot repair privileges that its seed was denied.

Before the first self-update, the seed must install a compatible binary, the generated unit and complete TLS inputs. The same explicitly supplied binary can serve as both the first seed and the fallback. This does not qualify an arbitrary older standalone binary.

Unit identities:

- Agent and supervisor: `User=root`, `Group=root`, `UMask=0077`.
- Host recovery: `User=root` (root's default primary group), `UMask=0077`, `Type=oneshot`, 45-second timeout.
- The independent watchdog/boot adapter uses local configuration and profile only; it needs no agent, cluster or TLS connection.

Keep host-root access to Redis, Docker, netlink/ip, systemd, process root and executable, `/proc/PID/environ` and `/proc/PID/map_files`. Do not add private namespaces, `ProtectProc` or capability pruning without native qualification on the target platform.

| Fixed writable area | Required identity and permissions |
|---|---|
| `/usr/local/sbin` | Fixed agent, supervisor, watchdog and recognized helpers, `0755`; create/rename/fsync parents |
| `/etc/systemd/system`, qualified `interfaces-config.service.d` | Fixed units, timer and adapters, `0644`; parent creation, daemon-reload, enable, qualified restart |
| `/etc/sonic-operator-agent` | Private `0700` directory; policy and TLS inputs `0600` |
| `/etc/sonic` | Host config, profile and SNMP generating inputs `0600`, plus native SONiC generating/persistent paths |
| `/host/sonic-operator-artifacts`, `-artifact-bootstrap`, `-artifact-content`, `-host-bootstrap`, `-host-journal`, `-vlan-journal`, `-breakout-journal`, `-network-journal` | Each full path has the prefix `/host/sonic-operator`; private stores `0700`, journal/protected files `0600`; durable parent creation and publication |
| `/run/sonic-operator-agent`, `/run/sonic-operator-artifacts` | Separate `0700` runtime directories for the private TLS receipt/material and the supervisor socket |

The agent validates private stores and their parents as trusted, root-owned non-symlinks. It never recursively chmods, copies, deletes or adopts existing data. Permission, storage or full-disk failures keep activation fenced. Keep runtime TLS receipts separate from source TLS files.

## Building a release and sources

### Build the binaries and release metadata

From a clean committed checkout:

```sh
GOMAXPROCS=3 make host-artifact-binaries
go run ./hack/host-artifact-release \
  --agent bin/host-artifact-release/agent \
  --supervisor bin/host-artifact-release/supervisor \
  --watchdog bin/host-artifact-release/watchdog \
  --controller bin/host-artifact-release/controller \
  --fallbacks bin/host-artifact-release/agent
```

- Build flags: Linux amd64, `CGO_ENABLED=0`, `-trimpath`, `-buildvcs=true`, `-ldflags='-s -w'`.
- The generator reads the actual ELF/Go build provenance and compiled capability declaration, rejects dirty or mismatched builds, and checks that each build commit exists in the repository and descends from every commit in `releasebundle.Floors` (empty by default; set it to fixes that releases must never fall below). Builds that declare the `host-imported-mac-unit-v1` capability must also descend from `releasebundle.ImportedMACFloors`, and the release records exactly the floors that apply to its agent build.
- Binary inspection and chunk publication use the same retained, bounded byte buffer, so replacing a build output file afterwards cannot substitute different bytes.
- Output: `config/agent/releases/<json-sha256>.json` (git-ignored; publish it with your release, not in source). Schema: `config/agent/releases/host-artifact-v1.schema.json`.
- Generated release JSON always contains `reviewRequired: true`. It describes the build; it does not authorize deployment.

### Generate source manifests

Pass the release path and the measured profile for your SONiC image:

```sh
go run ./hack/host-artifact-sources \
  --release "$RELEASE_JSON" --baseline "$BASELINE_NAME" \
  --profile config/agent/profiles/202411.1216684-48c2d4c3e.json \
  --agent bin/host-artifact-release/agent \
  --supervisor bin/host-artifact-release/supervisor \
  --watchdog bin/host-artifact-release/watchdog
```

Two measured base profiles are provided:

- `202411.1216684-48c2d4c3e.json`
- `202511.1217682-4784cca11.json` (uses chrony rather than NTPsec)

Flags:

| Flag | Default | Purpose |
|---|---|---|
| `--repo` | `.` | Source repository with ancestry objects |
| `--release` | | Content-addressed release JSON |
| `--profile` | | Measured base profile JSON |
| `--baseline` | | Explicit immutable baseline name |
| `--switch-input` | | Optional per-switch agent/hook metadata JSON |
| `--agent`, `--supervisor`, `--watchdog` | | Release binaries |
| `--additional-public-bytes` | `0` | Total bytes of separately prepared platform/public files |
| `--out` | `config/agent/profiles` | Content-addressed source manifest output |
| `--objects-out` | `bin/host-artifact-sources` | Immutable ConfigMap JSON output (large; keep out of Git) |

Outputs:

- Content-addressed source metadata is written to `config/agent/profiles/`.
- The (large) immutable ConfigMaps are written to `bin/host-artifact-sources/`, which is ignored by Git.
- Sources use ordered 256-KiB chunks and actual hashes, and contain **no UID**; UIDs are bound at publication.
- Sizing reserves the full TLS maximum (3 × 64 KiB) plus `--additional-public-bytes`. Aggregate checks run before any output is written and never raise the 128-MiB bundle limit.
- The generated policy covers host and agent files only. A platform policy needs its own exact destinations and consumers, verified for that specific switch; do not copy it to other switches. Recheck the complete aggregate size after adding it.

### Per-switch input

Without `--switch-input`, the output is an **unqualified base-profile source set**. To qualify a specific switch, pass a JSON file with:

- `switch`: the target switch.
- `agent`: typed agent options.
- `importedMACEnvironment` (optional): set to `sonic-dpu-none-v1` on images whose systemd generator adds a non-DPU `environment.conf` drop-in to `interfaces-config.service`. The tool then qualifies that generated drop-in and the native unit fragment exactly, and remeasures them after regeneration, bootstrap repair and boot. It does not take ownership of the generated file.
- `hooks`: imported legacy management-MAC hooks. Each hook supplies:
  - `declaration`: a `LegacyMACHook` with `kind`, observed base/active MAC and address tuple. For `kind: management-mac-python`, `hostname` is **required** (the Python helper selects its MAC by hostname) and must be a lowercase DNS label such as `leaf-01`. For `management-mac-shell`, `hostname` must be omitted. The legacy kind names `dc-management-only` and `set-management` from earlier releases are still accepted for installed hooks; new declarations should use the current names.
  - `interpreterSHA256`: the measured interpreter hash.
  - `helperFile`, `sourceHookFile` and `sourceHookSHA256`.

The tool checks pinned helper bytes and the captured activation-unit syntax, and a new profile includes import and interpreter evidence. Do not patch an installed profile or add exceptions to a measured base profile. Imports are never selected by switch name; a switch without its own qualified input stays unqualified.

## Publishing

Generated files are not publication. Deploy as follows:

1. Rebuild all four binaries from the source you intend to deploy and verify the release, policy, candidate and fallback hashes.
2. Create the software, profile and policy ConfigMaps with `immutable: true` in the resource namespace.
3. Read back the **server-returned `metadata.uid`**, immutability, key bytes and hashes. Bind every ordered reference in the API to that UID.
4. Create TLS material separately as immutable Secrets and bind their actual UIDs. Certificates, private keys and SNMP secrets must never be stored in Git, generator output or public manifests. Each TLS file read is bounded to 64 KiB; the generators do not need secret contents.
5. Compose the `bootstrap` and `hostRecovery` references and generated hashes, plus the complete agent recovery set (see below).
6. Seed every reader and the independent recovery service before enabling any new writers.
7. On the target switch, verify installation and effective units, the old hook/timer inventory, reservation and confirmation recovery, boot/interruption behavior and forwarding before relying on it.

`config/agent/reference-baseline.json` is publishable as an immutable bootstrap policy ConfigMap, but see [Baseline policy](#baseline-policy) before reusing it.

## Capabilities and accepted builds

`releaseinfo.Current()` is compiled into the controller, agent, supervisor and host recovery binaries.

- `--release-info` prints public source and capability metadata.
- The watchdog's `--check-installation` additionally qualifies the installed suite, profile/config and the measured watchdog binary.
- `ArtifactService.GetCapabilities` is read-only and works with mutation disabled. The optional client method is `ArtifactCapabilities(context.Context) (releaseinfo.Info, error)`.

Capabilities describe implemented support, not permission. Required names:

`routing-safe-writers-v1`, `artifact-reservation-v1`, `artifact-chunks-v1`, `host-observed-active-mac-v1`, `host-causal-runtime-v1`, `host-artifact-admission-v1`, `host-mac-ownership-v1`, `host-bootstrap-v1`

Unknown, duplicate or missing capabilities are rejected.

### Accepted agent builds

The immutable `bootstrap.policyRef` contains `agentBuilds`, keyed by the **actual AgentBinary SHA256**, each with a full 40-character `sourceCommit` and the exact capability set. At most 16 builds are allowed.

- Before confirmation, the client compares the loaded capabilities with that hash's policy entry.
- Native health independently hashes `/proc/PID/exe` against the installed executable and the accepted policy. Self-reported metadata cannot authorize unlisted code.
- Observe mode also accepts a capability declaration matching a previously accepted older release, so it can report `Unowned`, confirmed-old, `Staged` or `RolledBack` lifecycle state while a different candidate is desired. Phase, token, identity and reason remain visible, but `RuntimeVerified` is false for the candidate.
- Confirmation still requires the exact candidate declaration before the final freshness check. Staging still verifies the actual candidate and fallback hashes.
- Adding new accepted builds requires migrating the immutable baseline (see [Migrating the bootstrap baseline](#migrating-the-bootstrap-baseline)).

### Agent recovery set

Every agent, unit or TLS update requires all five recovery slots: `AgentBinary`, `AgentUnit`, `AgentCertificate`, `AgentKey`, `AgentCA`.

- Both the candidate and the protected old binary must be accepted builds. The fallback comes from last-confirmed content when present, not from possibly drifted disk bytes.
- The old TLS pair and trust must be restorable.
- Both units must exactly match the typed generator, keep the host/artifact guards and preserve the bind address and port.
- TLS-only manifests cannot satisfy foreign recovery.
- Recovery rechecks protected bytes and accepts only these five slots; future `Agent...` names are not included by prefix. The supervisor/watchdog, host profile, config, imported hooks/helpers and native receipts belong to the immutable bootstrap domain.

Never strip `macOwned`, `observedActiveMAC`, `bootRuntimeIdentity`, `packagesPrepared`, receipts or reservations to downgrade, including in `Idle` state with durable ownership. Older records remain readable; incomplete or below-floor recovery stays fenced.

## Status and ownership

Configuration, native runtime, durable persistence and recovery phase are reported independently.

- Observe-mode resources never report managed Ready.
- A resource is Ready only after confirmation and fresh independent checks.
- Reconciliation is blocked by: source deletion, source UID replacement, changes to the switch UID, endpoint or credential reference, and another bundle owner.
- Deleting a resource orphans the confirmed content and durable owner identity. It does not remove the working agent or transfer ownership to a recreated resource. Pending updates are still recovered independently.
- Status carries bounded, non-secret recovery reason codes.

Certificate rotation must keep a trust overlap that lets the controller connect with the new material. Otherwise the supervisor restores the previous working material.

## Recovery and safety guarantees

### Reservation

Before live mutation, the supervisor publishes `reservation.json` while holding the complete set of writer locks. Privately `Staged` content waiting for a boot is not a reservation.

- New pending publication and ordinary writes call `artifactstate.CheckPending` under the same locks.
- Existing recorded recovery uses `CheckRecovery` with its validated before/candidate authority only, and cannot publish a new request. This also covers confirmed boot restoration.
- If an already-pending foreign journal needs an agent that a candidate update broke, a recovery-only path replays the validated old agent files and restarts the agent. It does not replace platform files or change foreign journals. Once the agent is healthy, foreign recovery finishes and the remaining artifact rollback completes. Only a typed, validated foreign-pending exclusion may trigger this restricted path; ordinary native or readiness errors stay in their own transaction's recovery.
- The compiled capability set and accepted-binary floor supplement cooperating journals. A CLI flag alone cannot certify a rollback executable.

### Package installation and repair

The installer does not run `pip uninstall` or derive cleanup paths from a possibly incomplete installed `RECORD`.

- The qualified pure-Python wheel is converted into an exact, bounded candidate tree. Wheel member paths, hashes and `RECORD` must match the qualified package layout.
- Before either target (host or pmon) changes, the supervisor snapshots the complete allowed code and metadata/receipt tree and fsyncs the before/candidate hashes in its journal.
- One package lock covers inspection, publication, replacement and repair. Recovery rebuilds the protected before tree even when `RECORD` is missing or malformed.
- An installer that survives cancellation stays fenced until it exits and cannot overwrite a repair.
- Replacements are staged in a private, transaction-specific directory on the same filesystem, outside the inspected trees. Recovery removes only its own known, owner-protected temporaries and fsyncs the cleanup. Unknown files and symlinks block repair. Recovery does not depend on Python `finally` cleanup.
- Package payloads use digest-qualified filenames, so preparing a new pair cannot overwrite inherited recovery payloads.
- Package authority is kept per resource generation. An agent- or certificate-only generation carries over the last-confirmed package tree and launcher identity, so confirmation, rollback and later boot restoration keep that authority after old tokens are collected.
- For repair of owned sources, the known-good before tree comes from confirmed authority. The separately observed tree is only a compare-and-swap input; observed drift cannot authorize additional code paths.
- Older package journals without a preparation marker are normalized from their complete, hash-verified before/candidate payload pairs. Missing or corrupt legacy pairs are rejected without replacing the journal. New journals always record an explicit `packagesPrepared` value.

### Import provenance

pmon's four qualified Python daemons are launched through a generated `python3.11 -I -S` wrapper with explicit system and library paths.

- A source-only loader binds every `sonic_platform` import to declared hashes and canonical origins. Unrecorded shadow packages and stale bytecode cannot supply executed platform code. Package repair removes owned caches.
- Health inspects the complete package tree independently of `RECORD` and binds the launch proof to the interpreter, argv, boot, PID and start ticks, manifest and import paths.
- Hardware classes are not instantiated to collect the proof. Snapshot hashes alone are not accepted as proof of runtime adoption.

### Loaded TLS evidence

- At process start, the TLS loader publishes a private receipt for the exact server certificate/chain and client-auth CA bytes loaded into memory. The loaded material is retained privately until copied to the persistent recovery vault.
- Matching on-disk bytes without matching loaded-input evidence trigger a guarded restart.
- Fresh controller TLS peer certificates are compared with the declared chain, not just with a trusted issuer. Server issuer trust and client-auth CA trust stay separate.

### Boot activation and restoration

- Boot activation waits for both containers, their init jobs and the host platform installer to finish. Consumers that are not yet ready stay pending within the monotonic window; a fingerprint mismatch is reported as a separate failure.
- After the initial five-minute startup window, restoration of already-confirmed content enters `RecoveringBoot`, keeping the reservation and confirmed version. Each retry gets a fresh bounded budget, and successful activation is recorded durably so later health retries do not restart consumers repeatedly. This does not extend an unconfirmed candidate's confirmation window.
- Boot-runtime progress is scoped to the current host boot, pmon container ID and start time, generated launcher config and manifest, and daemon PID/start/command and launch-proof identities. It is recorded only after provenance verifies against an unchanged runtime fingerprint.
  - A new host boot restarts input restoration under the existing reservation.
  - Recreating pmon or regenerating its config invalidates progress and requalifies wrapped consumers.
  - Unchanged incarnations only retry health. Older boolean-only progress records are requalified.

### Transfer and staging

- A complete upload offset names a durable, hash-verified blob. On resume, a full-length partial is verified and published under the content-store lock, or reset if invalid. Both sides of the rename are synced before acknowledgement, including when the final acknowledgement was lost.
- Staging validates all destinations before copying any payload and keeps a 512-MiB filesystem recovery reserve.
- Abandoned attempts are cleaned on failure or startup only after durable journal references are established.
- Unknown journal versions, phases and ambiguous JSON stay blocked.

## Resource limits

| Limit | Value |
|---|---|
| Single binary | 96 MiB |
| Complete bundle | 128 MiB |
| gRPC receive ceiling (shared) | 4 MiB |
| Transfer chunk | 256 KiB |
| Private hash cache | 256 MiB |
| Metadata for observe, confirm, bootstrap and stage dispatch | 64 KiB |
| Each TLS file | 64 KiB |
| Staging filesystem reserve | 512 MiB |
| Accepted agent builds in policy | 16 |
| Unconfirmed update rollback | 5 minutes |
| Host recovery timeout | 45 seconds |

Split large binaries across immutable ConfigMaps that stay below the Kubernetes per-object size limit.

Artifact RPCs are admitted globally **before protobuf decoding**, and verified content is reused between reconciles. The Unix supervisor also admits only one request before decoding. Queued work honors cancellation; canceled work never invokes native mutation later.

Generated memory budgets:

| Unit | `GOMEMLIMIT` | `MemoryHigh` | `MemoryMax` |
|---|---|---|---|
| Supervisor | 512MiB | 768M | 1G |
| Main agent | 384MiB | 512M | 768M |

In local maximum-input tests, a 96-MiB chunked transfer added about 2.6 MiB of Go heap, and the largest admitted binary stage used about 333 MiB. These are implementation tests, not a stress qualification on an installed switch. As an example, one tested switch reported about 8 GB of RAM with about 5.5 GB available; check headroom on your own hardware.

## Baseline policy

The immutable baseline policy pins:

- the SONiC version file and the exact destination paths;
- native interpreter, daemon, generator, launcher and service fingerprints (sixteen in the example baseline).

A different image, package layout, generator or runtime input fails qualification.

For platform packages, the wheel and every declared host module must contain identical code. Runtime checks compare code and distribution metadata in host Python (3.13 in the example) and pmon Python 3.11. Generated SAI profile hashes and the running syncd `-p` argument must select `/etc/sai.d/sai.profile`. Only the observed persistent supervisor daemons must be running; completed init jobs are not treated as failed daemons.

`config/agent/reference-baseline.json` is an example baseline measured on one platform and SONiC image. Do not reuse it for other images or platforms; measure and publish a baseline for each.

## Retiring the legacy site hook

`retireLegacyHook: true` requires the complete site bundle.

1. The supervisor keeps the original rc-local hook and helper through staging and health verification.
2. After fresh controller confirmation, it journals `Retiring`, installs fixed inert owner markers at both legacy paths, reloads systemd and verifies persistence.
3. On failure or interruption, both original files are restored before recovery completes.
4. On later boots, the owner markers are restored from the confirmed content store.

The management-MAC hooks are not retired here; they are handled by the separate management ownership handoff.

## Host-service coordination

- `agent.hostConfig` enables the parallel HostService with the fixed persistent journal `/host/sonic-operator-host-journal`.
- `agent.hostGuard` keeps that cooperating guard after host writes are disabled. An agent update cannot remove or rebind an existing guard.
- Enable these only after HostService and its independently declared recovery/profile inputs are installed.

When the HostService recovery configuration exists, live artifact installation, activation, confirmation and rollback acquire its store lock, and pending management recovery takes precedence. The adapter recognizes the coordinated `/host` path and the `/var/lib/sonic-operator/host` baseline, and fails closed for unknown paths or record formats. It does not rewrite management settings, MAC helpers, system profiles or the host-recovery executable.

Lock order in the supervisor:

1. VLAN, breakout and network journal locks
2. Host-store fence
3. Artifact engine lock

Each journal parser validates checksums and pending recovery before artifact mutation. The qualified journal paths are `/host/sonic-operator-vlan-journal`, `/host/sonic-operator-breakout-journal` and `/host/sonic-operator-network-journal`. If the main agent is configured with different paths, adoption is blocked rather than creating a second writer namespace.
